# MoneyGun 결정 기록

최종 갱신: 2026-09-01

## D-001 — 제품 정체성

- 결정: MoneyGun을 자동 종목 추천기가 아니라 개인용 AI 투자회사 운영체제로 정의한다.
- 이유: 사용자가 원하는 핵심은 여러 가상 직원의 지속 협업과 자율 운용이며, 단일 모델의 예측 정확도만으로는 이를 충족하지 못한다.
- 상태: 승인된 초기 방향
- 후속 구체화: D-015가 초기 상품을 10만 원 집중투자 미션으로 정의한다.

## D-002 — MVP는 모의투자 전용

- 결정: MVP에서 실자금 주문을 제외한다.
- 이유: 전략 유효성, 데이터 시점, 주문 대사, 보안과 증권사 약관이 아직 검증되지 않았다.
- 재검토 조건: 60거래일 또는 100개 의사결정, 위험 위반 0건, 대사 오류 0건, 별도 릴리스 점검 통과.
- 상태: **D-011에 의해 대체됨**. 모의·그림자 검증은 유지하지만 MVP 결과에 소액 승인형 실거래 환경을 포함한다.

## D-003 — LLM은 주문 주체가 아님

- 결정: AI 직원은 조사·토론·제안만 하고, 위험 한도·수량·주문 가능 여부는 결정론적 엔진이 판단한다.
- 이유: 언어 모델의 환각과 비결정성이 실자금 주문 권한과 결합되는 것을 막기 위해서다.

## D-004 — 첫 전략은 장 종료 후 저빈도

- 결정: 종가 기반 후보 스캔과 다음 거래 세션의 모의 주문으로 시작한다.
- 이유: 사용자가 제공한 인사이트와 맞고, 고빈도보다 데이터·체결·운영 복잡도가 낮아 핵심 가설 검증에 적합하다.
- 주의: “종가 매수”가 종가 단일가 주문인지, 장 종료 후 신호 생성 후 다음 시가 주문인지 명확히 분리해 검증한다.

## D-005 — 소셜 자료의 역할

- 결정: X·Instagram은 전략 아이디어와 조사 질문의 출발점으로만 사용한다.
- 이유: 홍보성 성과, 선택 편향, 누락된 손실·비용·기간 때문에 운영 근거로 바로 사용할 수 없다.

## D-006 — 오픈소스는 역할별 후보로 평가

- 결정: 프레임워크 전체를 즉시 결합하지 않고 역할별 챌린저로 평가한다.
- 후보 역할:
  - Kronos: OHLCV 가격·변동성 예측 특징
  - Vibe-Trading: 개인 연구 워크스페이스, 메모리, 안전·감사 UX 참고
  - NautilusTrader: 연구와 실행의 동일 의미론을 위한 이벤트 기반 엔진 후보
  - skfolio: 포트폴리오 최적화·위험 측정 후보
  - TradingAgents: 직원 역할, 찬반 토론, 위험·포트폴리오 승인 흐름 참고
- 이유: 중복 기능, 라이선스, 유지보수, 데이터 규칙과 주문 안전성 검토가 선행되어야 한다.

## D-007 — 자기개선은 제안과 승격을 분리

- 결정: 에이전트가 새 규칙을 제안할 수는 있지만 운영 전략을 자동 변경하지 못한다.
- 이유: 실험 중 우연한 성과가 운영 규칙으로 침투하는 것을 막고 재현성과 책임 소재를 유지한다.

## D-008 — 한국 주식 우선의 순차적 이중 시장

- 결정: 최종 대상은 한국 주식과 미국 주식 모두지만, 한국 주식을 먼저 검증·모의운용하고 미국 주식은 후속 슬리브로 추가한다.
- 이유: 사용자의 우선순위를 반영하면서 거래시간·통화·휴장·비용이 다른 두 시장의 운영 오류를 한꺼번에 만들지 않기 위해서다.
- 미국 연구·그림자 조건: 한국 슬리브가 최소 20거래일 연속 데이터·신호 재현·주문 대사·위험 통제 품질 게이트를 통과한다.
- 미국 실주문 조건: 한국 집중투자 모드가 L2에 승격한다.

## D-009 — 첫 증권사 통합 후보는 키움 REST API

- 결정: 키움증권 REST API를 국내·미국 주식의 첫 통합 후보로 사용한다.
- 근거: [키움 REST API 공식 소개](https://openapi.kiwoom.com/intro?dummyVal=0)는 국내주식과 미국주식 지원, 모의투자, 계좌와 HTS ID 연결 및 API 사용 등록 요건을 안내한다. [공식 API 가이드](https://openapi.kiwoom.com/guide/apiguide)는 운영·모의 도메인과 국내·해외주식 API 범주를 구분한다.
- 설계 제약: 2026-08-31 공식 안내 기준 계좌·토큰당 세션은 하나이며, 모의계좌는 국내·미국 각각 TR별 초당 1회 제한이 있다. 작업 큐, 요청 조절, 재시도와 단일 주문 조정자를 설계에 포함하고 구현 시 최신 한도를 다시 확인한다.
- 제한: 공개 안내만으로 신한은행 연계 개설 계좌의 API 적격 여부는 확인되지 않았다. 해당 키움 계좌의 HTS ID 연결, 해외주식 거래 신청, REST API 등록 가능 여부를 직접 확인하기 전에는 연동을 시작하지 않는다.

## D-010 — 초기 위험 위임장은 보수적 모의운용 수치로 시작

- 결정: 실자금 한도가 아니라 모의운용 안전 기본값으로 [RISK_MANDATE.md](./RISK_MANDATE.md)의 수치를 제안한다.
- 핵심값: 총 주식 노출 80% 이하, 현금 20% 이상, 종목당 5% 이하, 거래당 계획손실 0.25% 이하, 당일 손실 -1%에서 신규 진입 중지, 고점 대비 -8%에서 전체 전략 중지.
- 재검토 조건: 최소 60거래일 또는 100개 의사결정 중 늦게 충족되는 시점, 그리고 시장별 비용·슬리피지 관측치 확보.
- 상태: **D-014에 의해 단계별 실거래 위임장으로 확장됨**

## D-011 — 제품 목표에 실거래 환경을 포함

- 결정: MoneyGun의 MVP 결과를 한국 주식 연구·그림자 운용에서 끝내지 않고, 품질 게이트를 통과한 키움 소액 승인형 실거래까지 포함한다. 이후 제한적 자율과 정상 자율 실거래로 승격한다.
- 이유: 사용자가 원하는 최종 효용은 보고서가 아니라 본인 계좌에서 안전하게 실행·대사되는 자동 운용이다.
- 경계: 실제 주문 활성화는 구현 완료, 계좌 적격성, 장애 훈련, `릴리스 점검`, 사용자 승인을 모두 통과한 뒤에만 가능하다.

## D-012 — 최초 운영 전략은 품질·모멘텀·종가후 신호 조합

- 결정: [STRATEGY_BASELINE.md](./STRATEGY_BASELINE.md)의 `QMB-EOD-KR-v1`을 최초 챔피언 후보로 사용한다.
- 핵심: 유동성 높은 한국 보통주, 재무 품질 최소 기준, 63일 상대 모멘텀, 20·60·120일 추세, 공식 공시 촉매, 다음 세션 지정가 진입, 5~20거래일 보유.
- 이유: Buffett·Berkshire의 품질, AQR의 정량 품질, 학술 모멘텀, Howard Marks의 위험·반론, Serenity의 공급망 분석과 사용자의 종가매매 관심을 한 전략 안에서 검증 가능한 규칙으로 결합한다.
- 제한: KRX 종가 단일가 매수는 시점 누출 가능성을 피하기 위해 별도 챌린저로 둔다.
- 상태: **D-015에 따라 안전투자 모드의 챔피언 후보로 이동**. 최초 집중투자 후보는 `FOCUS-MOMENTUM-KR-v1`이다.

## D-013 — 외부 에이전트는 조직 패턴만 채택

- 결정: TradingAgents의 전문 역할·Bull/Bear, FinRobot의 계산/서술 분리와 provenance, AI Hedge Fund의 mandate, Qlib의 연구 파이프라인을 참고하되 공개 프로젝트를 실주문 엔진으로 그대로 사용하지 않는다.
- 이유: 각 프로젝트는 연구·분석에 유용하지만 선택한 모델·데이터·비결정성에 따라 성과가 달라지고 실거래 안전성을 보증하지 않는다.
- 상세: [REFERENCE_BENCHMARKS.md](./REFERENCE_BENCHMARKS.md)

## D-014 — 단계별 실거래 권한과 기본 자본

- 결정: R0 연구 → R1 그림자 → L1 승인형 → L2 제한적 자율 → L3 정상 자율의 다섯 단계를 사용한다.
- L1 기본: 승인 자본 `min(계좌 예수금, 사용자 지정 자본, 500만 원)`, 총노출 20%, 최대 4종목, 거래당 위험 0.10%, 매수 사용자 승인.
- L2 기본: 총노출 50%, 거래당 위험 0.15%, 승인된 전략 안에서 매수·매도 자동.
- L3 기본: 총노출 80%, 거래당 위험 0.25%, 한국 56%·미국 24%·현금 20% 정상 목표.
- 이유: 자동 실거래라는 목표를 유지하면서 잘못된 코드·데이터·주문이 곧바로 전체 자본 손실로 연결되는 것을 막기 위해서다.
- 상세: [LIVE_TRADING_POLICY.md](./LIVE_TRADING_POLICY.md), [RISK_MANDATE.md](./RISK_MANDATE.md)
- 상태: **D-015와 D-016에 의해 모드·권한 분리 모델로 대체됨**

## D-015 — 초기 컨셉은 10만 원 집중투자 미션

- 결정: 첫 제품은 10만 원의 격리된 미션 자본으로 1,000만 원 장기 도전 목표를 추적하는 공격형 투자회사 컨셉으로 시작한다.
- 의미: 100배는 보장·승격 지표가 아니라 높은 상승 잠재력을 표현하는 미션 목표다. 미션 자본 전체 손실 가능성을 같은 화면에 표시한다.
- 위험 경계: 자동 추가입금, 다른 미션 자금 사용, 신용·레버리지, 손실 포지션 물타기를 금지한다. 운영 중지선은 고점 대비 -30%다.
- 이익 보호: 새 목표 사다리 달성 시 직전 사다리 이후 실현이익의 20%를 주문 불가 이익 금고에 잠근다.

## D-016 — 운용 모드와 자동화 권한 단계를 분리

- 결정: 집중투자·안전투자·장기투자는 전략·위험 위임장인 `모드`, R0·R1·L1·L2·L3는 주문 자동화 권한인 `단계`로 구분한다.
- 적용: 실제 한도는 두 체계 중 더 엄격한 값이다. L1은 어떤 모드든 총노출 50%와 매수 승인, L2부터 선택 모드의 전체 한도를 사용할 수 있다.
- 이유: 공격성, 투자기간과 자동 주문 권한을 하나의 설정으로 섞으면 검증되지 않은 전략이 곧바로 큰 권한을 얻을 수 있기 때문이다.
- 상세: [MODE_PROFILES.md](./MODE_PROFILES.md), [LIVE_TRADING_POLICY.md](./LIVE_TRADING_POLICY.md)

## D-017 — MVP는 프로세스 분리형 모듈러 모놀리스

- 결정: React/TypeScript PWA, Python/FastAPI API, 연구 워커, 단일 Execution Guardian, PostgreSQL, 객체 저장소로 구성한다.
- 이유: 한 사용자·한 계좌·일봉 전략에 마이크로서비스는 과도하지만 연구 장애와 실주문 경로는 프로세스·권한 수준에서 격리해야 한다.
- 메시징: PostgreSQL 작업 큐와 transactional outbox를 사용하고 Redis·Kafka·Temporal은 초기 비범위다.
- 실행 제약: 계좌·토큰당 단일 키움 세션은 Execution Guardian의 단일 리더 잠금으로 보장한다.
- 상세: [ARCHITECTURE.md](./ARCHITECTURE.md)

## D-018 — 주문 원장은 append-only 상태 머신

- 결정: 결정, 위험 판정, 승인, 주문, 체결, 대사와 사고를 덮어쓰지 않고 새 버전·이벤트로 기록한다.
- 핵심: 주문 시간초과는 실패가 아니라 `UNKNOWN`이며, 키움 조회로 확정하기 전에는 같은 주문을 다시 보내지 않는다.
- 이유: 실거래 자동화에서 가장 위험한 중복 주문과 사후 기록 변경을 차단하기 위해서다.

## D-019 — UX는 작전실이며 카지노 표현을 금지

- 결정: 어두운 투자 작전실, 위험 우선 정보 위계, 모바일 승인·중지 중심 UX를 사용한다.
- 100배 목표: 목표 사다리와 미션 자본 전액 손실 가능성을 같은 시각적 무게로 표시한다.
- 금지: 폭죽·로켓·현금비·슬롯머신·수익만 강조하는 애니메이션과 “필승” 문구.
- 상세: [ART_BIBLE.md](./ART_BIBLE.md)

## D-020 — 첫 실행 가능 산출물은 실거래 차단형 협업 프로토타입

- 결정: React/TypeScript 작전실과 Python/FastAPI 읽기 전용 샘플 API를 첫 실행 가능 기준선으로 만든다.
- 역할: DATA → NOVA(뉴스)·SERENITY(산업/공급망)·PULSE(차트) → BULL/BEAR → RISK → ACE(매수·매도 결정) → OPS(주문/대사)의 단방향 협업 흐름을 화면과 샘플 데이터에 고정했다.
- 안전 경계: 모든 종목은 `FICTIONAL`이며 `KIWOOM_TRADING_ENABLED=false`가 기본이다. 증권사 자격증명, 실제 시세 수집, 주문 전송 코드는 포함하지 않는다.
- 이유: 에이전트 수나 모델을 늘리기 전에 사용자가 역할·정보 위계·의사결정 흐름을 직접 보고 수정할 수 있는 기준점을 만들기 위해서다.
- 다음 구현: 투자 미션·모드·자본 원장 기반을 먼저 만들고, 그 위에 독립 보고서와 투자위원회 이벤트를 연결한다.

## D-021 — 픽셀 오피스를 서비스의 주 시각 은유로 사용

## D-022 — P0-1 로컬 원장은 SQLite 어댑터로 시작

## D-024 — P0는 결정론적 가상 데이터로 끝까지 연결하고 실데이터는 실패 폐쇄한다

## D-025 — 실데이터는 권한 명시 번들로 받고 OOS 승격은 모든 게이트의 AND 조건이다

- 입력: 서버는 설정된 `data/imports` 안의 단일 JSON 파일만 읽고 경로 이탈·50MB 초과·미래 봉·미래 재무·미래 근거를 거부한다. `KRX_AUTHORIZED_EXPORT` 또는 `LICENSED_VENDOR`와 이용 권한 근거가 함께 있어야 실데이터로 분류한다.
- OpenDART: 공식 공시검색·고유번호·단일회사 전체 재무제표 API만 사용하며 40자리 키가 없거나 공식 오류가 나면 실패 폐쇄한다.

- 현재 결과: 합성 fixture는 1,320거래일 배관 검증만 수행하며 소스 게이트를 무조건 실패한다. 성과가 좋아도 실데이터 증거로 사용할 수 없다.

## D-026 — P3의 20일 재생과 실제 20거래일 운영 증거를 분리

- 결정: 오늘 생성한 20개 날짜별 위원회 패키지는 `REPLAY`로 고정하며 실제 운영일에는 합산하지 않는다. 화면·API·감사 원장이 모두 `real_operating_days=0`, `qualifies_20_day_gate=false`를 표시한다.
- 자동화: 날짜별 실행은 SQLite `BEGIN IMMEDIATE` 잠금으로 한 작업자만 획득하고, 완료 날짜는 재실행하지 않으며 실패 날짜만 시도 횟수를 올려 재시도한다.
- 채점: 10거래일 뒤 결과가 존재하는 날짜만 9명 모두 채점한다. 정확도, Brier 기반 보정도, 검증 근거 비율, 과신 횟수를 기록하고 결과가 아직 없는 날짜는 대기로 둔다.
- 역할 구분: DATA·OPS는 프로세스 무결성, RISK는 무효화 가격 침범, 나머지 방향성 역할은 비용 차감 10일 수익 방향으로 평가한다.
- 완료 기준: P3 소프트웨어는 20/20 재생·중복 0·실패 0·9명 점수판으로 완료한다. 제품 운영 게이트는 실제 데이터로 20거래일이 경과해야 별도로 통과한다.

## D-027 — 한국어 이름과 역할을 시각 위계의 첫 줄에 둔다

## D-028 — 키움 연동은 조회 전용 클라이언트부터 물리적으로 분리한다

- 결정: 첫 키움 클라이언트는 OAuth 토큰과 국내 계좌평가잔고 `kt00018`만 허용한다. 매수·매도·정정·취소 메서드와 범용 요청 메서드를 두지 않는다.
- 비밀: App Key·Secret Key는 로컬 환경변수에서만 읽고, OAuth 토큰은 프로세스 메모리에만 둔다. 계좌 스냅샷은 계좌번호를 마스킹한 뒤 체크섬 기반 불변 레코드로 저장한다.
- 환경: `mock`을 기본으로 하고 `production`은 운영 App Key가 있을 때도 조회만 허용한다. 실제 주문은 향후 별도 Execution Guardian 프로세스로 구현한다.
- 이유: 조회 연동 검증이 주문 권한 획득으로 이어지는 권한 혼합을 차단하기 위해서다.

## D-029 — 그림자 주문은 별도 append-only 상태 기계다

- 결정: 최신 투자위원회의 `BUY_CANDIDATE`와 `PASS_RESEARCH_ONLY` 결과만 `CREATED → PRECHECKED → READY → SHADOW_SUBMITTED → SHADOW_FILLED/SHADOW_CANCELLED`로 전환한다.
- 보호: 같은 멱등 키는 같은 주문을 반환한다. 다음 장 갭 3% 초과는 취소, 1~3%는 수량 절반이며 모든 이벤트에 `broker_submitted=false`를 남긴다.
- 제한: 현재 다음 장 가격은 `DETERMINISTIC_SHADOW_FIXTURE`다. 실제 시세 기반 체결·계좌 잔고 대사를 완료하기 전에는 R1 운영 증거로 세지 않는다.

## D-031 — 주문 응답 불명은 UNKNOWN이며 재전송하지 않는다

- 결정: 지정가 매수·매도와 취소의 네트워크 시간초과·응답 파싱 실패는 `UNKNOWN` 또는 `CANCEL_UNKNOWN`으로 기록한다. 미체결·체결 조회로 확인하기 전 같은 주문을 다시 제출하지 않는다.
- 이유: 증권사 수신 여부가 불명인 상태에서 자동 재시도하면 중복 주문이 될 수 있다.

- 이유: 오래되었거나 내용이 변한 승인이 다른 주문에 재사용되는 것을 막는다.

## D-033 — P7 완료는 코드 준비이며 L2 활성화가 아니다

- 이유: 기능 구현 상태와 실제 운용 자격을 같은 완료 표시로 오해하지 않게 한다.

## D-036 — 일일 운영은 종가 후 한 번, 실패 폐쇄, 실주문 0건으로 시작한다

## D-037 — 종가매매는 전일 신호·다음 날 종가 진입의 독립 미션이다

## D-038 — 생존편향·지정상태 자격은 원본에서 서버가 도출한다

- 결정: `KRX_DAILY_PRICES`, `KRX_LISTING_LIFECYCLE`, `KRX_DESIGNATION_HISTORY` 원본 메타데이터와 원본·정규화 SHA-256을 모두 검증한 schema 2.0 번들만 생존편향·과거 지정상태 관문을 통과시킨다.
- 이유: 작성자가 완료 플래그만 입력하면 누락된 상장폐지·거래정지 종목을 탐지할 수 없고 실거래 성과가 과대평가될 수 있다.
- 결과: 현재 8종목 키움 스냅샷은 실제 데이터여도 자격 미달이다. KRX 공식 export 또는 계약 데이터의 전체 기간 번들이 필요하다.

## D-039 — OOS 방법론 변경은 프로토콜 버전으로 새 이력을 만든다

- 결정: 검증과 종가 위원회 레코드의 유일성에 `protocol_version`을 추가한다. 과거 공통 날짜 교집합 결과는 `LEGACY_COMMON_DATES-v1`, 새 시점별 동적 유니버스 결과는 `POINT_IN_TIME_DYNAMIC_UNIVERSE-v2`로 저장한다.
- 이유: 상장폐지 종목을 포함하면 거래 가능 종목과 날짜축이 달라지므로 기존 결과를 덮어쓰거나 같은 ID로 재사용하면 감사 계보가 깨진다.
- 결과: 기존 보고서는 그대로 조회할 수 있고, 새 방법론 결과와 위원회 결정은 독립 ID로 추가된다.
- 현재 증거: 동적 유니버스 방식은 집중투자 100거래·+164.54%·MDD -58.99%, 종가매매 164거래·+82.09%·MDD -17.05%이며 둘 다 `NOT_ELIGIBLE`이다.

## D-040 — 청산 결과만 성과로 확정하고 참여와 인과 기여를 구분

- 결정: 그림자·실거래는 매수와 매도가 FIFO로 연결된 뒤에만 비용 차감 순손익으로 확정한다. 전략, 시장 국면, 참여 직원, 청산 사유와 실행 품질을 불변 사후검토에 남긴다.
- 해석: 직원별 손익은 그 직원이 참여한 거래 결과이지 해당 직원이 수익을 만들었다는 인과 추정이 아니다. 인과 기여는 별도 제거 실험 전에는 표시하지 않는다.
- 자동 청산: 일일 운영은 무효화 가격 침범 또는 전략별 보유기간 완료를 공식 키움 시세로 확인해 그림자 결과를 닫는다.

## D-041 — 브로커 체결이 자본 원장의 진실이며 부분체결을 합치지 않는다

- 결정: 키움 체결번호를 `(주문의도, 브로커 체결키)` 유일키로 저장한다. 같은 수량·같은 가격의 체결도 체결번호가 다르면 별도 사건이다.
- 회계: 매수는 현금에서 노출원가로, 매도는 FIFO 노출원가에서 현금·실현손익으로 균형 전표를 추가한다. 대응 매수 lot이 없는 매도도 브로커 진실을 버리지 않고 중대 사고를 생성한다.
- 안전: 부분체결 잔량과 응답 불명 주문은 자동 재주문하지 않으며 조회 대사로만 상태를 확정한다.

## D-042 — 성과 악화는 신규 매수만 자동 중지

- 결정: 최소 20개 청산 결과부터 최근 20건 기대값 양수, 평균 절대 슬리피지 15bp 이하, p95 30bp 이하를 감시한다.
- 조치: 하나라도 실패하면 주문안 생성과 제출 시점에 신규 매수를 차단한다. 매도·대사·킬 스위치는 계속 작동한다. 시스템이 전략 수치를 자동 수정하지 않는다.

## D-043 — 이익 금고와 전략 변경은 별도 불변 통제

- 이익 금고: 실제 LIVE 청산으로 자산이 2·5·10·25·50·100배 사다리를 처음 넘을 때 구간 실현이익의 20%를 `RESERVED_PROFIT`으로 이동한다. 그림자 수익은 잠그지 않는다.
- 변경 승인: 전략·위임장·모드·위험 변경은 제안 내용의 SHA-256 범위와 소유자 결정을 기록한다. 승인 자체가 현행 설정을 바꾸지 않으며 별도 적용·버전 생성 절차가 필요하다.

## D-044 — 운영 배포는 PostgreSQL·OIDC·외부 비밀관리 관문을 모두 요구

- 저장소: 로컬은 SQLite, 운영은 `MONEYGUN_DATABASE_BACKEND=postgresql`일 때 psycopg 어댑터와 단일 쓰기 자문 잠금을 사용한다. 스키마 버전은 `schema_migrations`에 기록한다.
- 인증: `production` 환경의 `/health` 외 모든 요청은 HTTPS OIDC 발급자의 서명, issuer, audience, 만료를 검증한다. 주문·변경 승인 토큰은 별도 2차 통제로 유지한다.
- 배포: HTTPS 주소, 외부 비밀 주입, 오류 감시, 관리형 시점복구가 모두 설정되지 않으면 `LOCAL_ONLY`다. 공급자 선택 전에는 실거래 활성화를 허용하지 않는다.

## D-045 — 공공데이터 원본은 페이지 체크포인트와 시점 DB로 검증한다

- 결정: 금융위원회 주식시세·주식발행 API 원본은 페이지별 gzip JSON과 SHA-256으로 보존하고, KIND 화면 다운로드 원본은 변경하지 않은 채 별도 보존한다.

- 벤치마크: 공공 주식시세 API가 ETF를 반환하지 않으므로, 이미 감사된 키움 공식 `KODEX 200(069500)` 스냅샷을 5년 벤치마크로 결합하고 출처 스냅샷 ID·체크섬을 남긴다.

- 주문 경계: 이 수집·정규화 작업은 읽기 전용이며 `trading_enabled=false`를 변경하지 않는다.

## D-046 — KIND 공개 상세검색으로 시장조치 전체 페이지를 보존한다

- 결정: KIND `상세검색 → 시장조치`의 공개 검색·Excel 흐름에서 관리종목 `0350`, 투자주의환기 `0356`, 매매거래정지 및 정지해제 `0311`을 1년 이하 구간·100건 페이지로 수집한다.

## D-047 — 달력 5년과 거래일 경계를 분리하고 OOS를 v3로 보존한다

## D-048 — 장초 단타는 10분 관찰 후 제한형 장초돌파로 연구한다

- 결정: 새 모드는 `OPENING_RANGE`, 최초 전략 후보는 `OPEN-RANGE-KR-v1`로 한다. 09:00 즉시 진입하지 않고 09:00~09:10 장초 범위를 고정한 뒤 09:10~10:30에만 진입하며 11:00 전에 전량청산한다.
- 이유: 시가는 08:30~09:00 단일가로 형성되고 이후 연속매매로 바뀌므로 개장 직후는 가격발견·스프레드·가짜 돌파 위험이 크다. KOSPI 연구에서 장중 모멘텀 근거는 있으나 개별 종목의 매일 수익을 보장하지 않는다.
- 위험: 모드 최대 3회, L1 최대 2회, 한 번에 한 종목, 거래당 0.5%, 하루 -1% 또는 2연속 손실 중지를 기본으로 한다. 시장가·재진입·물타기·익일 보유는 금지한다.
- 역할: LLM 직원은 장전 제외 필터와 사후검토만 담당한다. 분봉·VWAP·수량·손절·주문 여부는 결정론적 엔진만 계산한다.
- 승격: 2년 시점고정 분봉·호가·VI, 마지막 126일 OOS, 300거래, +0.15R 기대값, Sharpe 1.2, DSR 0.95, MDD -8%, 비용·파라미터 견고성을 모두 통과한 뒤 60거래일·300신호 그림자 증거를 쌓는다.

## D-049 — 장초 모드는 원시 실시간 수집과 주문 자격을 분리한다

- 결정: 키움 WebSocket은 공개 시장 타입 `0B`·`0D`·`1h`·`0s`만 읽으며 계좌·주문 체결 타입을 구독하지 않는다. LOGIN·REG·PING은 공식 프로토콜로 처리하고 최대 20종목·30초·500프레임으로 제한한다.
- 정규화: 체결과 호가 FID를 거래소 시각의 1분봉·VWAP 입력으로 재구성하되, 장중 원시 보관본은 일별 유동성·과거 지정상태·동시간대 20일 중앙값이 결합되기 전까지 `HOLD`다.
- 실행: 재현 가능한 가상 세션은 필터·신호·위험수량·가상 체결·손절/목표/VWAP/시간청산·11시 전량청산의 소프트웨어 배관만 증명한다. fixture 결과는 어떤 성과여도 승격 자료가 될 수 없다.
- 권한: 생성되는 주문은 기존 그림자 원장에만 저장하며 `broker_submitted=false`, `trading_enabled=false`, `order_allowed=false`를 강제한다.

## D-050 — 장초돌파 v2는 고정 익절 대신 러너와 계층형 수익 잠금을 사용한다

- 결정: `OPEN-RANGE-KR-v1`의 `+1.5R` 전량 익절을 조용히 덮어쓰지 않고 `OPEN-RANGE-KR-v2` 챌린저를 만든다.
- 청산: 완성 1분봉 종가가 `+1.5R`에 도달하면 러너를 활성화한다. 2주 이상이면 절반을 익절하고, 1주면 전량을 유지한다. 이후 최고 완성 1분봉 종가 대비 `0.8%` 하락, `+3R` 또는 당일 `+10%` 이후에는 `0.5%` 하락으로 청산한다.
- 당일 잠금: 실현수익 `+5%`는 신규 진입만 막고 열린 포지션은 유지한다. 당일 추정 순수익 `+10%`는 추적폭을 강화하며, `+15%`는 전량청산과 당일 잠금을 실행한다. `+15%`는 성과 목표가 아니라 예외적 상한이다.
- 유지: 거래당 위험 `0.5%`, 당일 손실 `-1%`, 최대 3회, 2연속 손실, 11시 전량청산과 실주문 잠금은 완화하지 않는다.
- 검증: v2는 v1과 독립된 시점고정 OOS·비용·민감도·그림자 관문을 통과하기 전 실거래 자격이 없다.

## D-051 — 실거래 활성화는 미션별 순차 관문이며 배포 자격을 주문 직전에 재검사한다

- 결정: 집중투자·종가매매·장초 단타마다 전략 ID, 허용 신호 출처, 주문 가능 시간을 명시한다. 장초 단타는 `OPEN-RANGE-KR-v2`, `KIWOOM_OPENING_RANGE_REALTIME`, 09:10~10:30, R1 60거래일·300결정을 요구한다. 두 일봉 모드는 각각 60거래일·100결정을 요구한다.
- 신호: 장초 주문안은 승인된 `KIWOOM_REALTIME_ARCHIVE`의 당일 현재 완성 봉에서만 만들며 90초보다 오래된 봉과 `KIWOOM_REALTIME_RAW_ARCHIVE`를 거부한다. 생성 결과는 그림자 주문일 뿐 브로커로 전송하지 않는다.
- 실행: 모든 LIVE 주문 의도 생성·제출 직전에 최신 OOS 자격, 단계, 주문창, 포지션 수, 거래당 위험, 열린 위험, 계좌 대사와 배포 자격을 다시 검사한다. `LOCAL_ONLY` 배포는 키와 플래그가 있더라도 실패 폐쇄한다.
- UX: 운영센터의 실거래 활성화 센터는 세 미션의 통과·차단 관문과 다음 행동을 표시하지만, 비밀값을 읽거나 변경하고 주문을 제출하지 않는다.
- 이유: 소프트웨어 구현 완료를 전략 검증 완료나 실거래 허가로 오인하지 않고, 오래된 승인·신호와 로컬 개발 환경에서의 주문을 구조적으로 차단하기 위해서다.

## D-052 — 장초 OOS와 R1 그림자 증거를 분리하고 검증 프로토콜을 v2로 올린다

- 문제: 초기 `POINT_IN_TIME_INTRADAY-v1`은 Sharpe·DSR·낙폭·최악 월·견고성·2배 슬리피지가 고정 실패였고, OOS보다 뒤에 쌓아야 할 60일·300신호를 OOS 선행 관문에 포함해 R0→R1이 순환 차단됐다.
- 결정: `POINT_IN_TIME_INTRADAY-v2`는 봉인 OOS에서 일별 Sharpe, DSR, 자산곡선 MDD, 최악 월, Profit Factor와 R 기대값을 계산한다. ±20% 규칙 재실행과 슬리피지 2배 재실행도 코드가 직접 계산하며, R1 60일·300결정은 Execution Guardian의 별도 R1→L1 관문에서만 판정한다.
- 데이터: 승인된 `LICENSED_INTRADAY_VENDOR` 또는 `KIWOOM_REALTIME_ARCHIVE`만 허용한다. `OPENING_RANGE_ARCHIVE-v1` manifest, 시점고정·호가·VI 포함, 세션 출처 일치와 SHA-256을 모두 검사한 뒤 마지막 126거래일만 OOS로 실행한다.
- UX: 운영센터에 장초 아카이브 파일명 입력·OOS 실행과 `내일 아침 판정`을 추가한다. 이 경로는 검증과 그림자 기록만 수행하고 브로커 주문을 만들지 않는다.
- 결과: 검증기의 구조적 불가능 상태는 제거됐지만 승인된 2년 아카이브와 성과 통과 기록은 아직 없으므로 현재 실주문 자격은 그대로 없다.

## D-053 — 최초 60일을 5만 원 L0 실거래와 동시 그림자 학습 기간으로 바꾼다

- 결정: 기술·보안 릴리스 게이트를 통과한 뒤에는 전략 수익성 미검증 상태를 명시하고 5만 원으로 실제 주문을 허용한다. 같은 신호는 그림자 원장에도 남기며 모든 분석·토론·모드 기능을 열되 Execution Guardian의 자본·종목·주문·손실 통제를 우회할 수 없다.
- 버전: 15·30·45거래일에 동결 리뷰를 만들고 운영·위험·전략 변경을 v1.1~v1.n으로 전향 적용한다. 진입·청산 논리 변경은 별도 챌린저로 기록한다. 60거래일에는 전체 증거로 v2 후보를 만들되 자동 적용하거나 증액하지 않는다.
- 한도: 최대 실투입 50,000원, 주문예산 45,000원, 동시 1종목, 하루 신규 3건, 당일 -1,500원과 누적 -5,000원 중지선을 기본값으로 한다.
- 이유: 실제 평가손익·체결·슬리피지를 처음부터 직관적으로 관찰하면서도 실패의 최대 자본 범위를 고정하고, 더 큰 자본 승격과 전략 성과 검증은 분리한다.
- 구현 경계: 이 결정은 제품 정책 승인이다. 현재 코드의 실주문 잠금은 L0 설계·개발·릴리스 점검이 끝날 때까지 유지한다.

## D-054 — L0는 공통 5만 원 원장과 승인형 주문으로 구현한다

- 실행 원장: `mission_l0_pilot_001`을 집중·종가·장초 전략과 분리된 50,000원 자본 원장으로 둔다. 세 모드의 공식 `KIWOOM_*` 그림자 주문은 원본 미션·전략 계보를 유지한 채 이 원장에서만 실주문 의도로 전환한다.
- 통제: 주문당 45,000원, 동시 1종목, 하루 신규매수 3건, 당일 방어손익 -1,500원, 누적손익 -5,000원을 주문안 생성과 제출 직전에 모두 다시 검사한다. 손실선 도달 시 킬 스위치를 켜고 신규 주문을 거부한다.
- 승인: L0의 모든 주문은 5분 유효 범위 해시를 소유자가 승인해야 한다. LLM·분석 직원은 수량 계산, 자격증명 접근, 주문 제출을 하지 않는다.
- 검토: 실제 운용일 15·30·45·60일에 v1.1·v1.2·v1.3·v2.0 후보 보고서를 한 번만 동결한다. 후보는 자동 적용하거나 자본을 늘리지 않는다.
- 성과 표시: L0는 OOS 성과 미통과도 허용하지만 화면과 주문 기록에 `performance_qualified=false`를 남긴다. OOS·60일·검토 계보는 L1 확대의 필수조건으로 유지한다.
- 안전 잠금: 키움 운영 주문 키, 소유자 토큰, 릴리스 승인, 운영 배포 자격, 최신 호가·대사와 주문 시간이 모두 맞지 않으면 실제 브로커 호출은 발생하지 않는다.

## D-055 — L0 운영은 무과금 우선 `DESKTOP_LIVE` 프로필로 전환한다

- 결정: L0 5만 원 파일럿의 첫 운영 호스트는 AWS가 아니라 소유자의 Windows PC 한 대다. Web/API는 루프백에만 열고, 키움과 공식 데이터 공급자에 대한 아웃바운드 통신만 허용한다. 별도 클라우드 서버 비용은 발생시키지 않는다.
- 자격: 기존 `LOCAL_ONLY` 개발 환경은 계속 실주문을 금지한다. 자동 시작, 단일 Guardian, 로컬 PostgreSQL, Windows 비밀 저장소, 시간·전원·네트워크·키움 인증·등록 IP 검사, 기동 후 브로커 대사, 24시간 이내 검증 백업과 장애 훈련을 모두 통과한 별도 `DESKTOP_LIVE_ELIGIBLE` 자격을 만든다.
- 복구: 기동·재기동·절전 복귀는 항상 `RECOVERY_REQUIRED`로 시작한다. `SUBMITTING`·`UNKNOWN`을 포함한 미체결·체결·잔고를 조회해 차이 0을 확인하기 전에는 신규 주문도 자동 재제출도 허용하지 않는다.
- 인증: 외부 인바운드가 없는 L0에서는 OIDC·공인 HTTPS 대신 Windows 사용자 경계, 루프백 세션, 24자 이상 소유자 토큰과 5분 범위 주문 승인을 사용한다. App Key·Secret·OAuth 토큰은 `.env`가 아니라 Guardian 실행 계정의 Windows Credential Manager/DPAPI에 저장한다.
- 백업: 로컬 PostgreSQL의 일일 일관 백업·SHA-256 manifest·30개 회전본과 월간 격리 복원 훈련을 요구한다. 같은 디스크 복사본은 디스크 분실까지 보호하지 않는다는 제한을 UI와 릴리스 보고서에 표시한다.
- 한계: PC 전원, 절전, 가정 인터넷과 Windows 유지보수 상태에 의존하므로 24시간 무중단을 보장하지 않는다. 원격·모바일 접속, L2 무인운용, 다중 호스트, 더 높은 가용성 또는 자본 확대가 필요하면 관리형 배포 결정을 별도로 연다.
- 이전 결정과의 관계: D-044와 D-051의 `LOCAL_ONLY` 실주문 차단은 유지한다. `DESKTOP_LIVE`는 설정 하나로 우회하는 예외가 아니라 별도 구현·장애 훈련·릴리스 점검으로만 획득하는 운영 자격이다.

## D-056 — DESKTOP_LIVE L0는 SQLite 단일 작성자로 시작한다

- 발견: 대상 Windows PC에는 PostgreSQL 서버와 클라이언트 도구가 설치되어 있지 않았고, 기존 2.8M+ 시장 데이터와 L0 원장은 SQLite WAL에서 이미 검증·백업되고 있다.
- 결정: 5만 원·한 PC·한 API·한 Execution Guardian인 L0에서는 기존 SQLite 원장을 유지한다. Windows 이름 기반 뮤텍스와 예약 작업의 `IgnoreNew` 정책으로 두 번째 API·Supervisor를 차단하고, 기동마다 `RECOVERY_REQUIRED`와 키움 대사를 요구한다.
- 백업: SQLite 온라인 백업·SHA-256·격리 복원 훈련을 그대로 사용한다. 24시간 이내 백업과 31일 이내 복원 훈련, 암호화된 저장 볼륨 확인이 없으면 `DESKTOP_LIVE_ELIGIBLE`이 아니다.
- 승격: PostgreSQL 지원과 `pg_dump`·격리 복원 구현은 보존한다. L1/L2, 다중 워커, 원격 관리형 배포 또는 SQLite 쓰기 경합이 관측될 때 신규 전용 PostgreSQL DB로 이관한다.
- 이유: L0에서 새 DB 설치·대용량 이관을 필수화하면 무과금·최소 개입 목표에 비해 운영 복잡도와 이관 사고면이 더 커진다. 단일 작성자와 실패 폐쇄를 유지하면 SQLite가 현재 단계의 가장 작은 충분한 구조다.

## D-057 — Windows Home 백업은 소유자 토큰 기반 AES-256-GCM으로 암호화한다

- 발견: 대상 PC는 Windows 10 Home이며 BitLocker/EFS 저장 폴더 암호화를 사용할 수 없다. 단순 확인 플래그만 켜면 평문 SQLite 백업을 암호화됐다고 잘못 판정한다.
- 결정: `DESKTOP_LIVE` SQLite 온라인 백업을 소유자 토큰에서 scrypt로 파생한 키와 매 백업의 무작위 salt·nonce를 사용하는 AES-256-GCM 컨테이너로 저장한다. SHA-256은 암호문에 적용하고 복원 훈련은 인증 태그 검증·복호화·SQLite 무결성 검사를 모두 수행한다.
- 경계: 소유자 토큰은 DPAPI 파일에서 실행 프로세스로만 가져오고 백업 파일·DB·로그에 기록하지 않는다. 같은 PC의 30개 회전본은 DB 손상 복구용이며 디스크 분실·PC 고장까지 보호하려면 별도 암호화 외장 매체가 필요하다.
- 실패 폐쇄: 토큰이 없거나 24자 미만, 형식·인증 태그 불일치, 복호화·무결성 검사 실패 시 백업/복원 관문은 통과하지 않는다.

## D-058 — 5만 원 종가 파일럿은 전시장 유동성 순위와 소형주 안전 하한을 함께 쓴다

- 버전: 기존 OOS 챌린저 `CLOSE-AUCTION-KR-v2`를 덮어쓰지 않고, L0 전용 당일 후보 전략을 `CLOSE-AUCTION-KR-v3-L0`로 추가한다. v3는 수익성 OOS 통과를 뜻하지 않는다.
- 발견: 키움 공식 `ka10030` 거래대금 순위에서 KOSPI·KOSDAQ 전체와 1만 원 미만 구간을 각각 연속조회한다. 자격 번들의 보통주 생애주기와 지정·정지 이력을 당일 기준으로 대조한 뒤 2,000~45,000원 종목만 상세 조회한다.
- 소형주: 시가총액 500억~1조 원을 화면에 `SMALL_CAP`으로 표시한다. 작다는 이유로 가산점은 주지 않으며 20일 중앙 거래대금 50억 원, 당일 거래대금 30억 원, 거래량 1.2~6배, 당일 +1~15%, 당일 고가권 70% 이상과 추세·시장 국면을 함께 통과해야 한다. 500억 원 미만 초소형주는 제외한다.
- 시간: 15:05~15:10에 후보를 고정하고 15:20~15:27에 최신 15초 호가와 30초 계좌 대사를 다시 확인한다. Windows 로컬 스케줄러는 승인 대기 실주문 의도까지만 멱등 생성한다.
- 실행 경계: L0는 자동 승인·자동 제출을 금지한다. 소유자가 화면에서 5분 범위를 승인하고 별도로 제출해야만 Execution Guardian이 주문 직전 전체 관문을 재검사한다. 기존 보유종목은 MoneyGun 체결로 생긴 관리 종목이 아니면 계속 대사 대상에서 제외한다.

## D-059 — 모든 모드는 하나의 L0 실행 계약을 공유하고 전략 자격은 분리한다

- 결정: 집중 `FOCUS-MOMENTUM-KR-v2-L0`, 장초 `OPEN-RANGE-KR-v3-L0`, 안전
  `BALANCED-TREND-KR-v1-L0`, 장기 `LONG-TREND-KR-v1-L0`를 별도 불변 전략 버전으로
  추가한다. 기존 v1/v2 OOS 기록은 덮어쓰지 않는다.
- 공통 계약: 네 전략은 후보 미션에서 근거를 만들지만 주문 자본·보유·손익은 모두
  `mission_l0_pilot_001`에 귀속한다. 최대 45,000원 BUY, 관리 1종목, 손실선,

  중앙 거래대금이 없으므로 일거래대금 10% 프록시는 L0에서만 쓴다.

  데이터 결합 전까지 기술적 장기 후보일 뿐 완전한 품질·가치 전략으로 부르지 않는다.
- 활성화: 멀티모드 스케줄러는 구현하되 기본값은 꺼 둔다. 변경 전체에 대한 릴리스
  재검사와 소유자 재승인 전에는 자동 준비 프로세스를 켜지 않는다.

## D-060 — 김뉴스는 공식 공시 감시와 신규 매수 차단을 담당한다

- 분류: `NOVA-DISCLOSURE-RISK-v1`은 제목의 명시적 위험어만 결정론적으로 분류한다.
  방향성·목표가·수량을 추측하지 않고 LLM은 주문 계산이나 제출에 관여하지 않는다.
- 통제: 횡령·배임·상장폐지·거래정지 등 CRITICAL 공시는 발견 후 72시간 해당 종목의
  신규 BUY를 차단한다. 유상증자·전환사채·감자·정정 등 WARNING은 소유자 확인 전까지
  차단한다. 확인 기록이 CRITICAL 차단을 해제하지 않으며 SELL·대사·긴급중지는 막지 않는다.
- 신선도: 감시 자동화가 켜진 운영 프로필에서는 최근 성공 수집이 없거나 실패했거나
  15분보다 오래되면 모든 신규 BUY를 실패 폐쇄한다. 주문안 생성과 실제 제출 직전에
  같은 검사를 반복한다.

## D-061 — L0-AUTO-v1은 5만 원 경계를 유지한 소유자 위임 자동 실행이다

- 권한: 소유자가 `L0-AUTO-v1`과 5만 원 전액 손실 가능성을 명시 확인하면 L0에서도
  주문별 클릭을 위임할 수 있다. 이는 L2 승격, 전략 성과 통과, 자본 증액을 뜻하지 않는다.
- 범위: 위임 활성화 시각 **이후** 생성된 `mission_l0_pilot_001` 주문 의도만 자동 승인·제출한다.
  활성화 전 대기 주문은 소급 실행하지 않는다. 위임 승인은
  `OWNER_DELEGATED_L0_AUTO` 행위자로 감사 원장에 남는다.
- 실행: 후보·청산 스케줄러는 계속 조회와 주문 의도 준비만 담당하고, 별도 10초 단일
  실행 워커가 최신 호가·계좌 대사 뒤 Execution Guardian을 호출한다. 지정가 주문창이
  끝난 미체결 잔량은 취소하고 부분 체결 잔량을 다시 주문하지 않는다.
- 불변 안전선: 50,000원 원장, 주문당 45,000원, 관리 종목 1개, 하루 신규 3건,
  당일 -1,500원, 누적 -5,000원, 기존 보유종목 제외, 김뉴스 BUY 차단, 킬 스위치,
  시장가·신용·미수·공매도 금지와 `UNKNOWN` 무재시도를 완화하지 않는다.
- 실패 폐쇄: `SUBMITTING`·`UNKNOWN`·`CANCEL_UNKNOWN`, 뉴스 비신선, 대사 차이,
  오래된 호가, 런타임 미복구, 배포 미자격 중 하나라도 있으면 자동화를 중지한다.
- 출처: 현재 자동 수집 출처는 OpenDART뿐이다. 라이선스 계약이나 공식 API 자격증명이
  없는 포털·SNS·일반 뉴스는 수집하지 않으며 UI에 `NOT_CONFIGURED`로 표시한다.
- 실행 경계: 뉴스 스케줄러는 루프백 API만 호출하고 브로커 키·승인 토큰·주문 제출
  능력이 없다. 실제 주문 권한은 계속 Execution Guardian 한 곳에만 있다.

## D-062 — 김데이터는 공식 자격 데이터를 매일 검증 후 원자적으로 승격한다

- 일정: 로컬 PC가 켜진 상태에서 거래일 18:30~23:55에 본 실행하고, 데이터 게시 지연이나
  PC 종료를 보완하기 위해 매일 06:00~08:20에 한 번 더 시도한다. 공공데이터 API가 실제로
  게시한 가장 최근 완료 거래일을 기준일로 사용한다.
- 원본: 금융위원회 주식시세·주식발행정보와 KIND 상세검색의 투자주의 `0341`, 투자경고
  `0342`, 투자위험 `0343`, 관리 `0350`, 환기 `0356`, 거래정지·재개 `0311`을 5년 구간으로
  수집한다. 기준일별 독립 staging을 사용해 다른 기간의 체크포인트를 재사용하지 않는다.
- 벤치마크: 공공 주식시세 API가 ETF를 제공하지 않으므로 새 정규화 DB의 `KODEX 200`
  구간은 운영 DB에 이미 품질 PASS로 감사된 키움 공식 스냅샷에서 결합한다. 1,200거래일
  미만이거나 출처가 없으면 승격하지 않고 실패 폐쇄한다.
- 승격: 생존편향·상장폐지·6종 시장조치·벤치마크·원본과 정규화 SHA-256 검사를 모두 통과한
  schema 2.0 번들만 활성 스냅샷으로 추가한다. 실패 또는 PC 종료 시 기존 활성 스냅샷은
  바꾸지 않고 3일 신선도 제한에 따라 신규 매수를 계속 차단한다.
- 권한: 갱신 스케줄러는 루프백 데이터 API만 호출하고 주문 키·소유자 승인 토큰·브로커 주문
  제출 능력을 갖지 않는다. 시작·성공·실패는 감사 체인과 운영 상태 파일에 함께 기록한다.
- 저장: 검증 재현성을 위해 기준일별 5년 원본과 정규화 DB를 보존한다. 자동 보존기한·정리는
  디스크 사용량을 관측한 뒤 별도 결정하며 이번 버전은 자료를 자동 삭제하지 않는다.

## D-063 — GitHub 포트폴리오는 익명화된 단일 공개 이력으로 배포한다

- 브랜드: 야간 투자 작전실의 정밀함을 표현한 픽셀형 금고·차트 SVG를 공식 로고와 favicon으로
  사용한다. 총기·카지노·수익 보장 이미지는 사용하지 않는다.
- 공개 범위: 소스·테스트·제품 문서·안전 경계는 공개하되 `.env`, DPAPI 파일, DB, 시장 원본,
  백업, 로그, 계좌·주문 식별자와 실제 보유종목은 포함하지 않는다.
- 이력: 로컬 개발 이력은 보존한다. GitHub 최초 공개는 현재 검증 트리에서 개인 운영 식별자를
  제거한 단일 루트 커밋으로 만들어 과거 커밋의 운영 흔적을 외부에 노출하지 않는다.
- 권리: 포트폴리오 열람을 위한 공개이며 별도 오픈소스 라이선스를 임의로 부여하지 않는다.
